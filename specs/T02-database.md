# T02 — Database and test harness

**Goal:** a schema that evolves safely and tests that stay fast as they grow. **Out of scope:** endpoints.

## Acceptance criteria

| Criterion | How | Tested by |
|---|---|---|
| Tables for documents, extractions, proposals, reviewer decisions | SQLAlchemy models in `app/<feature>/models.py`, plus `claims` (holds the status) and `extraction_line_items` | `tests/core/test_migrations_db.py` |
| Every migration upgrades and downgrades clean | Migrations from `make revision` (autogenerate); functions/triggers via alembic-utils | Stairway: each revision up → down → up on a scratch DB, then `base` leaves only `alembic_version` |
| Only the transitions from the transition rules can happen | `claim_status_transitions` table + trigger on `claims` | `tests/claims/test_transitions_db.py`: all 10 allowed pairs; refused via service and via raw SQL |
| Tests are isolated | Each run gets its own `<name>_test` database (created, migrated, dropped); each test runs in a transaction that is rolled back | Isolation test run twice; each run must see only its own claim |

## Design decisions

**Async SQLAlchemy** (from T01). The engine and session wiring stay as they are; migrations use the same
`build_engine(Settings)`.

**Chose typed columns for extracted fields over JSONB field.** `duplicate_of` is set when policy 1.4 applies; money stays
`NUMERIC` and comes back as `Decimal`; the contract's rules (`total > 0`, currency format) become CHECK
constraints. Line items are a child table.
*Rejected: one JSONB column*, which avoids migrations while the shape changes, but makes every query
cast JSON and loses DB-level checks. JSONB is still used where data is written and read whole:
proposal `reasons` and `missing_information`, extraction `warnings`, claim `attendees`, reviewer
`corrected_fields` (partial by definition).

**Statuses as lookup tables** (`claim_statuses`, `claim_status_transitions`), seeded by a data
migration. Adding a status or transition is a new row, not an `ALTER TYPE`. *Rejected: PostgreSQL enum
types*, which can't drop values. Other enum-like columns (`decision`, `category`, `document_type`) are
`VARCHAR` + a named CHECK for the same reason.

**Proposals are append-only.** A trigger refuses `UPDATE`; a re-run after `needs_info` inserts a new
proposal. Reviewer decisions are a separate table (one per proposal), so the agent's proposal is never
overwritten.

**Users are not a table yet.** `employee_sub` / `reviewer_sub` hold the Cognito subject; a `users` table
can add foreign keys later without rewriting them.

## A migration must drop a constraint whose name the database generated. How does it know the name, in every environment?

- Added `Base.metadata` which adds a naming convention (`ck_<table>_<name>`,
  `fk_<table>_<column>_<referred>`, …), so every constraint, index and key is created with a
  deterministic name, the same in every environment. A later migration drops it by that name.
- Enum CHECKs are declared explicitly (`one_of(...)`), because SQLAlchemy's built-in `Enum` constraint
  doesn't get the convention in autogenerated migrations.

## Where does the transition rule live so that neither the API nor the extraction pipeline can bypass it?

- **In the database.** A `BEFORE INSERT OR UPDATE OF status` trigger on `claims` refuses any change not
  listed in `claim_status_transitions` (SQLSTATE 23514), and new claims must start in `pending_upload`.
  The API, the extraction worker, a Lambda or raw SQL all go through it.
- `app/claims/service.py:transition()` doesn't repeat the rule: it turns the trigger's refusal into
  `InvalidTransitionError` and updates with compare-and-set (`WHERE status = :current`), so two workers can't both move a claim. In the case of two workers updating the same claim, worker 1 would succeed and worker 2 would get a `ConcurrentTransitionError`.

## Test plan

- Integration (own test database per run, rolled back per test): every allowed transition; one refused
  through the service and one through raw SQL; isolation;
  migration stairway on a scratch database.
- Unit tests stay database-free (`make test-unit`).
- Coverage ≥ 80% enforced in CI.
